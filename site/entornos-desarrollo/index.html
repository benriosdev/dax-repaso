    Entornos de Desarrollo

    Recorre todo el ciclo de vida del software: desde qué es un programa y cómo se traduce a código ejecutable, hasta las pruebas, la documentación y el modelado con UML.

    1. Desarrollo de software

    Un programa es un conjunto de instrucciones (código fuente) que hay que traducir a un formato que la máquina entienda. El código objeto es el resultado intermedio de compilar, y el código ejecutable es el binario final; en lenguajes como Java, una máquina virtual (JVM) ejecuta un código intermedio (bytecode) independiente del sistema operativo.

    • Tipos de lenguajes: compilados (se traducen enteros antes de ejecutar) frente a interpretados (se ejecutan línea a línea), y de bajo frente a alto nivel según su cercanía al hardware.
    • Fases del desarrollo: análisis del problema, diseño de la solución, codificación, pruebas, documentación, mantenimiento y explotación — el mismo ciclo que se ve en Programación, aplicado a nivel de proyecto completo.
    • Metodologías ágiles (Scrum, Kanban...): dividen el proyecto en iteraciones cortas con entregas frecuentes, frente a los modelos clásicos en cascada donde cada fase se cierra antes de pasar a la siguiente.
    • Proceso de obtención de código: compiladores, intérpretes y las herramientas que transforman el código fuente en algo ejecutable.

    2. Instalación y uso de entornos de desarrollo

    Un IDE integra en una sola aplicación el editor de código, el compilador/intérprete, el depurador y el control de versiones, agilizando todo el flujo de trabajo frente a usar herramientas sueltas.

    La instalación suele seguir tres pasos: descargar el IDE desde su web oficial, instalar (o configurar) el JDK u otro entorno de ejecución que el IDE necesite, y por último instalar los plugins específicos del lenguaje o framework con el que se vaya a trabajar (por ejemplo, soporte para Java, control de versiones Git o análisis de código). Elegir un IDE u otro (Eclipse, IntelliJ IDEA, Visual Studio Code...) depende sobre todo del lenguaje y del ecosistema del proyecto.

    3. Diseño y realización de pruebas

    Antes de dar por bueno un programa hay que planificar qué se va a probar y cómo.

    • Estrategias y automatización: definir de antemano qué casos probar y automatizar su ejecución para repetirlos en cada cambio de código.
    • Cobertura, valores límite y clases de equivalencia: técnicas para elegir qué casos de prueba merece la pena escribir sin tener que probar absolutamente todas las combinaciones posibles.
    • Pruebas funcionales (¿hace lo que debe?), estructurales (¿se ejecuta bien el código internamente?) y de regresión (¿sigue funcionando lo que ya funcionaba, tras un cambio?).
    • Calidad del software: métricas y buenas prácticas que van más allá de "que funcione", como mantenibilidad y legibilidad.

    4. Documentación y optimización

    • Refactorización: reorganizar código existente para mejorar su estructura sin cambiar su comportamiento externo, aplicando patrones ya conocidos y evitando el "código espagueti".
    • Control de versiones (Git): registra el historial de cambios de un proyecto y permite que varias personas trabajen a la vez sin pisarse el trabajo.
    • Documentación y comentarios: explicar el porqué de decisiones no evidentes en el código, para quien lo mantenga en el futuro (incluido uno mismo).

    5. Introducción al UML

    UML (Unified Modeling Language) es un lenguaje gráfico estándar para representar el diseño de un sistema software antes o durante su construcción, independiente del lenguaje de programación que se use luego.

    ¿Sabías que...?

    UML no es un invento reciente: lo estandarizó en 1997 el OMG (Object Management Group) unificando varias notaciones de diseño distintas que competían entre sí en los años 90.

    6. Ingeniería inversa de software

    Consiste en analizar un programa ya construido (a veces sin código fuente disponible) para entender cómo funciona por dentro, ya sea para documentarlo, migrarlo o auditarlo. Tiene implicaciones éticas y legales claras: solo es lícita sobre software propio o con autorización expresa.

    7. Elaboración de diagramas de clases

    El diagrama de clases UML representa las clases de un sistema, sus atributos, métodos y las relaciones entre ellas (herencia, asociación, composición), de forma muy similar a como se diseña una clase en POO pero a nivel gráfico y antes de escribir una sola línea de código.

    8. Elaboración de diagramas de comportamiento

    Mientras el diagrama de clases es estático, estos diagramas UML muestran cómo se comporta el sistema en el tiempo.

    • Diagramas de casos de uso: qué puede hacer cada actor (usuario o sistema externo) con la aplicación.
    • Diagramas de interacción: cómo se comunican los objetos entre sí para llevar a cabo una operación.
    • Diagramas de estados: los distintos estados por los que pasa un objeto y qué eventos provocan cada transición.
    • Diagramas de actividades: el flujo de un proceso paso a paso, con decisiones y ramificaciones, similar a un diagrama de flujo.

    Git y GitHub en la práctica, de benrios.dev/hola-git/git y benrios.dev/hola-git/github

    Git no es lo mismo que GitHub

    Git es el sistema de control de versiones distribuido que funciona en tu ordenador: guarda el historial de cambios (qué cambió, quién y cuándo). GitHub es una plataforma en la nube que aloja repositorios Git y añade funciones para colaborar, como Pull Requests, forks y GitHub Pages.

    Lo primero después de instalar Git es configurar tu identidad (usa el mismo nombre y email que en GitHub):

    git config --global user.name "Tu Nombre"
git config --global user.email "tu@email.com"

    Comandos esenciales

    ComandoPara qué sirve
    git initCrear un repositorio en la carpeta actual
    git clone URLCopiar un repositorio remoto a tu equipo
    git statusVer el estado de los archivos
    git add .Pasar cambios al área de preparación (staging)
    git commit -m "..."Guardar una instantánea con un mensaje
    git push origin mainSubir los commits al remoto
    git pull origin mainDescargar y fusionar los cambios del remoto
    git checkout -b ramaCrear una rama y cambiarse a ella
    git merge ramaFusionar una rama con la actual

    Flujo de trabajo en equipo

    1. Crear o clonar el repositorio.
    2. Crear una rama para cada funcionalidad o corrección, por ejemplo feature/login o fix/pago.
    3. Hacer cambios y guardarlos con add y commit, en commits pequeños y con mensajes claros.
    4. Subir la rama con push.
    5. Abrir un Pull Request para que el equipo revise los cambios.
    6. Fusionar en la rama principal cuando esté aprobado.

    Para contribuir a un proyecto ajeno se hace un fork (tu propia copia del repositorio) y se abre el Pull Request contra el original.

    GitFlow y merge vs. rebase

    GitFlow organiza las ramas así:

    • main: el código en producción, siempre estable.
    • develop: donde se integra el desarrollo.
    • feature y release: salen de develop, para nuevas funcionalidades y para preparar lanzamientos.
    • hotfix: sale de main, para correcciones urgentes.

    Buenas prácticas

    • Nunca subir archivos sensibles (.env, credenciales). Usa .gitignore.
    • Revisar los cambios con git diff antes de hacer commit.
    • Hacer pull antes de push para evitar conflictos.

    Versionado semántico

    El versionado semántico (SemVer) numera las versiones como MAYOR.MENOR.PARCHE y da significado a cada cifra: se incrementa MAYOR cuando se hacen cambios incompatibles en la API, MENOR cuando se añade funcionalidad compatible con lo anterior y PARCHE cuando se corrigen errores sin cambiar la API. También admite etiquetas de preversión (como 1.0.0-alpha) y metadatos de compilación. Así, quien depende de tu software sabe si actualizar es seguro solo con mirar el número.

    Integración continua

    Según la definición de Martin Fowler, la integración continua consiste en que cada miembro del equipo integra sus cambios en el código común al menos una vez al día, y cada integración se verifica con una compilación automática que incluye las pruebas. Su beneficio principal es detectar los errores de integración lo antes posible: al haber cambiado poco código entre una integración y otra, es mucho más fácil localizar y resolver el problema.

    La pirámide de pruebas

    La pirámide de pruebas propone tener muchas pruebas unitarias en la base, menos pruebas de integración o de servicio en el medio y muy pocas pruebas de interfaz de usuario de extremo a extremo en la cima. La razón es que las pruebas de interfaz son lentas, frágiles y caras de mantener, mientras que las unitarias son rápidas y señalan exactamente dónde está el fallo.

    Puntos clave

    • El ciclo de vida del software se repite en cada proyecto: análisis, diseño, codificación, pruebas, documentación, mantenimiento.
    • Las metodologías ágiles entregan en iteraciones cortas, frente al modelo en cascada que cierra cada fase antes de la siguiente.
    • Cobertura, valores límite y clases de equivalencia ayudan a elegir qué casos de prueba merece la pena escribir.
    • Refactorizar cambia la estructura interna del código sin cambiar su comportamiento externo.
    • UML representa tanto la estructura estática (diagrama de clases) como el comportamiento dinámico (casos de uso, estados, actividades).

    Ponte a prueba

    ¿Qué diferencia hay entre una prueba funcional y una estructural?

    La funcional comprueba si el software hace lo que debe (desde fuera); la estructural comprueba cómo se ejecuta el código internamente.

    ¿Qué es una prueba de regresión?

    Comprobar que un cambio en el código no ha roto algo que ya funcionaba antes.

    ¿Qué representa un diagrama de casos de uso?

    Qué puede hacer cada actor (usuario o sistema externo) con la aplicación.

    ¿Qué significa refactorizar código?

    Reorganizar código existente para mejorar su estructura interna sin cambiar su comportamiento externo.
