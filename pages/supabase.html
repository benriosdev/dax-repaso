    Supabase

    Backend as a Service construido sobre PostgreSQL: base de datos, autenticación, almacenamiento de archivos y APIs generadas automáticamente, pensado como alternativa de código abierto a Firebase.

    0. Qué es Supabase

    Supabase es una plataforma que da a cada proyecto una base de datos PostgreSQL completa, junto con un conjunto de servicios adicionales (autenticación, almacenamiento, funciones de servidor, tiempo real) que normalmente habría que montar por separado. Al ser PostgreSQL estándar por debajo, los datos no quedan atrapados en un formato propietario: se puede conectar con cualquier herramienta o driver de Postgres.

    ¿Sabías que...?

    El nombre "Supabase" viene de "Super" + "Database", y su mascota es un elefante — un guiño al elefante que es el logo oficial de PostgreSQL desde hace más de veinte años.

    1. Base de datos y API automática

    Cada tabla que se crea en la base de datos de un proyecto Supabase obtiene automáticamente una API REST (a través de PostgREST) y una API GraphQL, sin escribir ningún endpoint a mano. Esto permite consultar y modificar los datos directamente desde el frontend con una librería cliente.

    const { data } = await supabase
  .from("tareas")
  .select("id, titulo, completada");

    Row Level Security (RLS)

    Como la API queda expuesta directamente, Supabase se apoya en las políticas de seguridad a nivel de fila (RLS) de PostgreSQL: reglas que definen, para cada tabla, qué filas puede leer o modificar cada usuario. Sin una política activa, por defecto no se puede acceder a los datos desde el cliente.

    CLI y desarrollo local

    La CLI de Supabase (supabase init, supabase start) levanta una copia completa del stack (base de datos, Auth, Storage...) en el propio ordenador con Docker, para desarrollar y probar sin depender de internet ni tocar el proyecto real. Los cambios en el esquema se gestionan como migraciones: archivos SQL versionados que se aplican en orden, tanto en local como al desplegar a producción con supabase link y supabase db push.

    2. Autenticación

    El módulo Auth gestiona el registro e inicio de sesión de usuarios: email y contraseña, enlaces mágicos (sin contraseña) y proveedores externos (OAuth) como Google o GitHub. Cada usuario autenticado queda disponible dentro de las políticas de RLS, de forma que las reglas de acceso pueden basarse en quién ha iniciado sesión.

    Integración con la base de datos

    Supabase guarda los usuarios en un esquema propio de PostgreSQL, así que una política de RLS puede comprobar directamente, por ejemplo, que el user_id de una fila coincida con el usuario autenticado antes de permitir leerla o modificarla.

    3. Storage y Edge Functions

    Storage gestiona archivos (imágenes, documentos, vídeos) organizados en buckets, con las mismas políticas de RLS que la base de datos: se puede restringir quién sube o descarga cada archivo con las mismas reglas que se usan para las tablas.

    Edge Functions

    Son funciones de servidor (escritas en TypeScript, sobre el runtime Deno) que se ejecutan cerca de la ubicación de cada usuario para reducir la latencia. Se usan para lógica que no debe vivir en el cliente: procesar un pago, enviar un email o llamar a una API externa con una clave secreta.

    4. Realtime

    El módulo Realtime permite que un cliente se suscriba a los cambios de una tabla (inserciones, actualizaciones, borrados) y los reciba al instante, sin tener que consultar la base de datos periódicamente. Es la base para construir funciones como notificaciones en vivo o listas que se actualizan solas cuando otro usuario añade un dato.

    Sincronización de estado

    Además de escuchar cambios en la base de datos, Realtime permite sincronizar y difundir estados entre varios clientes conectados al mismo canal (por ejemplo, quién está en línea en ese momento), útil en aplicaciones colaborativas.

    Puntos clave

    • Supabase da a cada proyecto una base de datos PostgreSQL estándar, sin formato propietario.
    • Cada tabla obtiene automáticamente una API REST y GraphQL, sin escribir endpoints a mano.
    • Row Level Security (RLS) controla, fila a fila, qué puede leer o modificar cada usuario.
    • Storage gestiona archivos con las mismas políticas de RLS que la base de datos.
    • Edge Functions ejecutan lógica de servidor; Realtime notifica cambios de la base de datos al instante.

    Ponte a prueba

    ¿Sobre qué motor de base de datos está construido Supabase?

    PostgreSQL.

    ¿Qué obtiene automáticamente cada tabla que se crea en un proyecto Supabase?

    Una API REST (vía PostgREST) y una API GraphQL, sin necesidad de escribir endpoints manualmente.

    ¿Para qué sirve Row Level Security (RLS)?

    Para definir, fila a fila, qué puede leer o modificar cada usuario en una tabla; sin una política activa, no se puede acceder a los datos desde el cliente.

    ¿Cuándo usarías una Edge Function en vez de ejecutar la lógica en el cliente?

    Cuando la lógica no debe vivir en el navegador, por ejemplo al usar una clave secreta, procesar un pago o llamar a una API externa de forma segura.
