    Git

    Control de versiones distribuido: la base de cómo se gestiona el código en cualquier proyecto profesional, funcione con GitHub, GitLab, Bitbucket o sin ningún servidor remoto.

    0. Qué es el control de versiones

    Un sistema de control de versiones registra el historial de cambios de un proyecto: quién cambió qué, cuándo y por qué, y permite volver a cualquier punto anterior sin miedo a "romper" el código. Git es un sistema distribuido: cada copia local del proyecto tiene el historial completo, no solo una referencia a un servidor central, así que se puede trabajar (hacer commits, ver el historial) sin conexión a internet.

    ¿Sabías que...?

    Git lo creó Linus Torvalds en 2005, el mismo creador de Linux, porque las herramientas de control de versiones que usaba el kernel de Linux en ese momento no daban abasto con miles de colaboradores trabajando en paralelo.

    Git no es GitHub

    Git es la herramienta que se ejecuta en tu ordenador; GitHub es solo una de varias plataformas (junto a GitLab o Bitbucket) donde alojar repositorios Git en remoto y colaborar. Se puede usar Git en un proyecto sin subirlo nunca a ningún servidor.

    1. El repositorio y los commits

    git init convierte una carpeta normal en un repositorio Git, creando una carpeta oculta .git donde se guarda todo el historial. A partir de ahí, el flujo de trabajo básico tiene tres zonas: el directorio de trabajo (los archivos tal cual los ves), el staging area o índice (los cambios que has marcado para el próximo commit) y el historial de commits ya guardados.

    git init
git add archivo.txt        # mueve el cambio al staging area
git commit -m "Primer commit"   # guarda el cambio en el historial

    Comandos para revisar el estado

    git status muestra qué archivos están modificados, en staging o sin seguimiento (untracked); git log lista el historial de commits; git diff muestra línea a línea qué ha cambiado antes de decidir si lo añades al staging area.

    2. Ramas (branching)

    Una rama es una línea de desarrollo independiente: permite trabajar en una funcionalidad o corrección sin tocar la rama principal (normalmente main) hasta que esté lista. Crear y cambiar de rama es barato en Git, así que es habitual tener una rama por cada tarea.

    Comandos básicos

    git branch nombre-rama crea una rama nueva; git switch nombre-rama (o el más antiguo git checkout nombre-rama) cambia a ella; git merge nombre-rama, ejecutado desde main, incorpora los cambios de esa rama.

    Conflictos de merge

    Un conflicto ocurre cuando dos ramas han modificado las mismas líneas de un archivo de forma distinta y Git no puede decidir por sí solo cuál usar. Git marca el archivo con <<<<<<<, ======= y >>>>>>> señalando ambas versiones; hay que editarlo a mano, elegir el resultado final y hacer un nuevo commit para cerrar el conflicto.

    3. Deshacer cambios

    Git ofrece varias formas de deshacer, según en qué punto estés. git restore archivo.txt descarta cambios no confirmados en el directorio de trabajo, volviendo a la última versión guardada. .gitignore es un archivo de texto donde se listan patrones de archivos que Git debe ignorar siempre (como carpetas de dependencias o archivos de configuración local), para que nunca lleguen a un commit.

    git reset vs. git revert

    git reset mueve el historial hacia atrás como si esos commits no hubieran existido (útil solo en ramas que no has compartido con nadie más, porque reescribe el historial). git revert es más seguro para trabajo compartido: crea un commit nuevo que deshace los cambios de un commit anterior, sin borrar el historial.

    4. Trabajar con remotos

    Un remoto es una copia del repositorio alojada en otro sitio (típicamente GitHub o GitLab). git clone url descarga un repositorio remoto completo por primera vez; git remote -v muestra los remotos configurados.

    Sincronizar cambios

    git push sube tus commits locales al remoto; git pull descarga y fusiona los cambios del remoto en tu rama local (equivale a un git fetch seguido de un git merge); git fetch por sí solo solo descarga la información sin fusionarla, para poder revisarla antes.

    Puntos clave

    • Git es distribuido: cada copia local tiene el historial completo, no solo el servidor remoto.
    • El flujo básico es directorio de trabajo → staging area (git add) → historial (git commit).
    • Las ramas permiten desarrollar en paralelo sin afectar a main hasta hacer merge.
    • git reset reescribe el historial (solo en ramas no compartidas); git revert es seguro porque añade un commit nuevo.
    • git push/git pull sincronizan con el remoto; Git no es lo mismo que GitHub.

    Ponte a prueba

    ¿Qué diferencia hay entre el directorio de trabajo, el staging area y el historial de commits?

    El directorio de trabajo son los archivos tal cual los ves; el staging area son los cambios marcados con git add para el próximo commit; el historial son los commits ya guardados de forma permanente.

    ¿Por qué es más seguro usar git revert que git reset en una rama compartida?

    Porque git revert añade un commit nuevo que deshace los cambios sin borrar el historial existente, mientras que git reset reescribe el historial, lo que puede descolocar a quien ya tenía esos commits.

    ¿Cuándo aparece un conflicto de merge?

    Cuando dos ramas han modificado las mismas líneas de un archivo de forma distinta y Git no puede decidir automáticamente cuál de las dos versiones usar.

    ¿Para qué sirve el archivo .gitignore?

    Para listar patrones de archivos o carpetas que Git debe ignorar siempre, de forma que nunca se incluyan en un commit (por ejemplo, carpetas de dependencias o configuración local).
